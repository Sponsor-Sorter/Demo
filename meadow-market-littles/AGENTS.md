# Littles play quality

These are the user's standing requirements for this children's game, for ages roughly3–6.

- Use full-screen illustrated farm scenes, with all controls inside the scene. Keep large, separate touch targets of at least44CSSpixels on compact phones. More difficult levels must not make controls too small or crowded.
- Keep introduction text directly over the full-screen scene without flat or translucent colour strips behind it. Use clear light lettering with a subtle dark text shadow; preserve normal button surfaces. Check the final combined stylesheet cascade on the actual phone so a later theme cannot reintroduce dark text or a coloured text backing.
- Completion-based matching, memory and observation puzzles need genuine difficulty progression: more choices, longer patterns, more details or closer alternatives, within preschool-friendly limits. Let players return to an easier challenge. Creative free play does not need incorrect-answer rules.
- After two genuine incorrect attempts on the current step, offer a clearly glowing hint button. Tapping it should highlight the correct choice, matching card or destination. It must not automatically complete the answer, award progress, charge a try or reveal unrelated answers. Reset the miss counter and hint after a correct step. A cancelled gesture is not a wrong guess.
- Existing game IDs, progress, records, saves and completed-round allowance must survive upgrades. Failed or abandoned attempts remain free. Use the existing shared completion and reward path.
- Use only approved Jade/Hope, Rhys/Noah and Jay/Mike recordings. Generate new instructions with the matching approved farmer where needed. Keep narration aligned with the current step, including pause, resume and celebrations.
- Before public activation, run meaningful rules/input checks, inspect compact phone and tablet layouts, and play complete rounds in the installed phone app. Include advanced difficulty and actual incorrect guesses/hints. Coordinate the shared phone and publishing windows; preserve other apps, device settings, accounts and saved data.
- Changes can be deployed behind the existing private quality gate for native acceptance. Clear the private cohort only after acceptance, then verify ordinary public access and an app restart. Do not claim Google Play approval when the listing remains in review.

## Production accounts during QA

- Reuse the existing Samsung and browser QA identities and their persistent storage. Do not create fresh production anonymous users for test permutations, retries, isolated browser profiles or public smoke checks. Do not run the archived live signup factories or their `init` / `fresh-public` provisioning modes.
- Run rules, account lifecycle and isolated browser checks against mocked clients or local fixtures with no production authentication requests. Use the guarded `tools/littles-local/serve-bug-picnic.cjs` server and preload `tools/littles-local/qa-network.cjs` for Node QA. Do not remove its CSP or network guards to make a test pass. An empty browser profile pointed at the full live app automatically provisions an anonymous identity; it is not an isolated test environment.
- Keep family, ordinary player and purchased accounts separate from disposable fixtures. A default nickname, anonymous status, empty cloud save or automated user agent alone does not establish that an account can be deleted. Cleanup needs explicit owner criteria (such as the authorised 27 November keep-20 manifest) or exact fixture provenance, plus the Admin purchase, staff and evidence-retention checks.
