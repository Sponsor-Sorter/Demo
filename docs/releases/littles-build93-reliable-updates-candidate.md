# Littles build 93 candidate

The installed phone showed the updater's connection-or-install error after one normal Install update tap. Its particular failed request is unknown. All 1,076 public precache URLs subsequently returned successful desktop GET responses. In an isolated desktop browser, the exact build 92 worker became redundant when one optional picture returned a controlled HTTP 503; its all-successful control installed and activated.

Build 93 installs the matching HTML, JavaScript, styles and configuration as one required cache bundle. A failed critical request still rejects installation and leaves the earlier bundle intact. Installed critical code comes from its matching cache, so a later network response cannot silently replace it under an older version URL.

Optional pictures and voices no longer make network requests during installation or activation. Already downloaded optional assets migrate locally with four concurrent copies. Normal use fetches fresh assets and falls back to the current or retained earlier resource cache on HTTP errors and offline failures. Cleanup retains at most two resource caches and only recognises numeric `meadow-littles-vN` resource-cache names; drawing, account, saved progress and other-app stores are untouched.

An optional asset that has never been downloaded still needs a connection on first use. Earlier available pictures and recordings remain usable offline through the retained fallback.

Validation is recorded in the candidate packet: ten focused worker cases, the existing twenty-seven updater cases, twelve advert-readiness cases and forty-seven reward/adapter/account-transport cases. Browser optional-failure, critical-failure and successful-control fixtures are recorded separately. These are desktop/source checks, not native update or advert acceptance.

This candidate changes no native build, provider configuration, backend, quality gate, subscription, allowance or farmer recording. Public extra-round flags remain off. Source publication, an actual successful phone update and the outstanding real advert/SDK-close/signed-reward tests require separate coordinated stages.
